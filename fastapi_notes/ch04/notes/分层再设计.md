## 4.2 为什么 service 不该返回 ORM 对象

### 4.2.1 DetachedInstanceError 从哪来

SQLAlchemy 的 ORM 对象和创建它的 Session 绑在一起。Session 关闭后：

- **已经加载的字段**：数据在内存里，还能读
- **还没加载的关系属性**：需要再查库，但 Session 没了 → `DetachedInstanceError`

案例文件：`fastapi_notes/ch04/code/01_orm_vs_dto.py`

```plain
--- ① ORM 对象: 已加载的字段, Session 关了也能读 ---
    Session 里:       张三 888.00
    Session 关掉后:   张三 888.00 (还能读, 因为已经加载了)

--- ② ORM 对象: 未加载的关系属性, Session 关了就读不了 ---
    Session 里: 只取了用户对象, 故意不碰 roles
    报错了: DetachedInstanceError
```

**注意这个陷阱**：如果 Session 里恰好访问过一次 `roles`，数据进了内存，关掉后还能读——测试时凑巧通过，上线遇到别的路径就炸。

### 4.2.2 三个具体问题

| 问题 | 后果 |
| --- | --- |
| 关系属性懒加载失败 | `DetachedInstanceError` |
| 不能直接 JSON 序列化 | `Decimal`、`datetime` 要特殊处理，还会带出 `_sa_instance_state` |
| 表结构泄漏到接口层 | 加一列就自动出现在响应里，容易泄露敏感字段 |

### 4.2.3 DTO 为什么能解决

```python
with SessionLocal() as db:
    user = db.get(User, 1)
    dto = UserOut.model_validate(user)      # 在 Session 内转好
# Session 关掉后, dto 是纯数据, 随便用
```

```plain
--- ③ DTO: 在 Session 里就转好, 出去随便用 ---
    转成 DTO: 张三 888.00
    Session 关掉后读 DTO: 张三 888.00
    DTO 转成 dict:       {'id': 1, 'username': '张三', ..., 'created_at': '2026-11-03T16:07:59'}
```

> **通俗理解**：ORM 对象像"还插着网线的电脑"，拔了线就用不了；DTO 像"打印出来的一张纸"，复印、传阅、存档都没问题。

## 4.3 什么时候转 DTO

| 场景 | 要不要转 |
| --- | --- |
| service 内部临时用一下对象 | 不用，ORM 对象够用 |
| 返回给路由、要进响应 | **要转**，路由层不该碰 Session |
| 要塞进 Redis | **必须转**（见 redis ch03） |
| 要在后台任务里用 | **必须转**，那时 Session 已经关了 |
| 要跨进程/发消息 | **必须转** |

**原则**：**Session 的边界就是 DTO 的边界**。谁跨出 `with Session(...)` 或 `get_db` 的 `yield`，谁就该是纯数据。

## 4.4 排序参数：为什么必须白名单

### 4.4.1 危险写法

```python
@app.get("/unsafe")
def unsafe(sort: str = "id"):
    db.execute(text(f"SELECT ... ORDER BY {sort}"))     # ❌ 用户输入直接拼进去
```

案例实测：

```plain
--- ② 不安全写法: 注入一段 SQL 试试 ---
    状态码: 400  响应: {'detail': 'SQL 出错: ProgrammingError'}
    复杂表达式也被执行了: 200 ORDER BY (CASE WHEN 1=1 THEN id ELSE balance END)
```

第一条被数据库语法挡下了，但第二条**复杂表达式成功执行**——说明输入确实进了 SQL，只是这次没造成破坏。

### 4.4.2 三种写法对比

| 写法 | 非法值什么时候被挡 | 文档里能看到可选值吗 |
| --- | --- | --- |
| 直接拼字符串 | 不挡（危险） | 不能 |
| 手工判断 `if sort not in ...` | 业务逻辑里，返回 400 | 不能 |
| `Literal[...]` | **入口就 422**，进不到业务 | **能** |

案例实测：

```plain
--- ③ 白名单写法: 非法值被挡下 ---
    状态码: 400  响应: sort 只支持: ['id', '-id', 'balance', ...]

--- ④ Literal 写法: 入口就 422, 连业务逻辑都进不去 ---
    状态码: 422
    错误: Input should be 'id', '-id', 'balance' or '-balance'
```

### 4.4.3 为什么首选 Literal

```python
SortField = Literal["id", "-id", "balance", "-balance", "created_at", "-created_at"]
```

三个好处：

1. **安全**：非法值进不来，从根上消除注入面
2. **文档**：`/docs` 的下拉框自动列出六种，前端不用猜
3. **少写代码**：不用手写 `if ... raise HTTPException`

> **通俗理解**：白名单像点菜——菜单上有的才能点；直接拼字符串像"你写什么厨房就做什么"，早晚出事。

## 4.5 在项目里落地

### 4.5.1 `PageParams` 加排序字段

```python
SortField = Literal["id", "-id", "balance", "-balance", "created_at", "-created_at"]

class PageParams:
    def __init__(
        self,
        page: int = Query(1, ge=1, ...),
        size: int = Query(10, ge=1, le=100, ...),
        sort: SortField = Query("-id", description="排序方式, 减号表示降序"),
    ) -> None:
        self.page = page
        self.size = size
        self.sort = sort
        self.offset = (page - 1) * size
```

### 4.5.2 service 用白名单映射

```python
SORT_MAP = {
    "id": User.id,
    "-id": User.id.desc(),
    "balance": User.balance,
    "-balance": User.balance.desc(),
    "created_at": User.created_at,
    "-created_at": User.created_at.desc(),
}

def list_users(db, page=1, size=10, sort="-id"):
    order_by = SORT_MAP.get(sort, User.id.desc())    # 再兜一层
    ...
```

**为什么 service 还要兜一层**：`PageParams` 只保证 HTTP 入口合法，但 service 也可能被定时任务、命令行直接调用。

### 4.5.3 实测

```plain
sort=id         -> [(1, '888.00'), (2, '400.00'), (3, '100.00')]
sort=-id        -> [(908, '0.00'), (3, '100.00'), (2, '400.00')]
sort=balance    -> [(908, '0.00'), (3, '100.00'), (2, '400.00')]
sort=-balance   -> [(1, '888.00'), (2, '400.00'), (3, '100.00')]
```

## 4.6 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `DetachedInstanceError` | Session 关掉后访问未加载的关系 | 在 Session 内转成 DTO |
| `TypeError: Object of type Decimal is not JSON serializable` | 直接序列化 ORM 对象 | 用 `model_dump(mode="json")` |
| 响应里意外多出字段 | 直接返回 ORM 对象，没经过 schema 裁剪 | 统一走 `response_model` |
| 排序参数改不了结果 | 路由没把参数传给 service | 检查调用链 |
| `sort=xxx` 返回 500 | 没有白名单，拼出了非法 SQL | 改成 `Literal` + `SORT_MAP` |
| 测试里 `sort` 无效 | service 的 `map.get()` 默认值写错 | 确认默认分支是合理的排序 |

## 4.7 本章小结

1. ORM 对象和 Session 绑定，Session 关闭后访问未加载的关系会 `DetachedInstanceError`。
2. **Session 的边界就是 DTO 的边界**：跨层的、要缓存的、要进后台任务的，都该是 DTO。
3. DTO 能自由序列化、能裁剪字段，还能防止表结构泄漏到接口层。
4. 排序字段必须用白名单，不能把用户输入拼进 SQL。
5. `Literal` 比手工 `if` 更好：入口就挡、文档自动列、代码更少。
6. 项目已支持 `sort` 参数（6 种取值），并补了 3 个测试。
