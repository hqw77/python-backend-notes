# FastAPI 第二章 · 中间件与请求生命周期

## 2.1 学习目标

上一章讲"依赖"——只对声明了它的接口生效。这一章讲"中间件"——**每一个请求都会经过**。学完应该能做到：

1. 说清一个请求从进入到返回经过哪些环节
2. 会写 `@app.middleware("http")`，知道 `call_next` 前后各是什么阶段
3. 能实现三个常用能力：请求 id 透传、耗时统计、CORS
4. 理解多个中间件的"洋葱顺序"
5. 知道两个坑：中间件异常不被 `exception_handler` 捕获、不要在中间件里做重活

前置知识：第一章（依赖注入）、`mysql_notes` 第六章（异常映射）。

> **本章的读法**：五个案例都是独立小应用，可以直接跑。
> 最后一节把"请求 id + 耗时"真正接进 `project/`，并补测试。

## 2.2 一个请求的完整生命周期

```plain
   客户端
     │  HTTP 请求
     ▼
┌──────────────────┐
│  uvicorn         │  接收 TCP、解析 HTTP
└────────┬─────────┘
         ▼
┌──────────────────┐
│  中间件(外层)     │  ← 本章讲这里
│  中间件(内层)     │
└────────┬─────────┘
         ▼
┌──────────────────┐
│  路由匹配         │  /users/1 -> get_user
└────────┬─────────┘
         ▼
┌──────────────────┐
│  依赖注入         │  get_db / get_current_user
└────────┬─────────┘
         ▼
┌──────────────────┐
│  路由函数         │  调 service
└────────┬─────────┘
         ▼
┌──────────────────┐
│  异常处理器       │  业务异常 -> HTTP 响应
└────────┬─────────┘
         ▼
      响应返回（中间件再从里到外走一遍）
```

**关键点**：中间件在最外层，所以它能看到所有请求；也正因为在外层，它**拿不到路由参数**（那时候还没匹配到路由）。

| | 中间件 | 依赖（Depends） |
| --- | --- | --- |
| 作用范围 | 所有请求 | 只对声明了它的接口 |
| 能拿路由参数吗 | 不能 | 能（`user_id: int`） |
| 能改响应吗 | 能（加响应头） | 不能直接改 |
| 适合 | 请求 id、耗时、CORS、日志 | 鉴权、取数据库、参数校验 |

> **通俗理解**：中间件是小区的门禁，所有人进出都要经过；依赖是某个房间的钥匙，只有要去那个房间的人才需要。

## 2.3 中间件怎么写

### 2.3.1 最小结构

```python
@app.middleware("http")
async def my_middleware(request: Request, call_next):
    # ① 请求阶段：请求进来
    response = await call_next(request)      # ② 交给后面的中间件/路由
    # ③ 响应阶段：结果回来了
    return response
```

`call_next(request)` 这一句就是**分界线**：它之前是"请求进来"，它之后是"响应返回"。

### 2.3.2 跑一遍看顺序

案例文件：`fastapi_notes/ch02/code/01_middleware_basic.py`

```plain
--- ① 正常请求: 中间件包住路由 ---
    执行顺序:
      1. 中间件 进入  GET /hello
      2. 路由函数执行
      3. 中间件 返回  status=200
```

### 2.3.3 路由抛异常时，后半段不执行

```plain
--- ③ 路由抛异常时, 中间件的后半段不会执行 ---
    执行顺序:
      1. 中间件 进入  GET /boom
      2. 路由函数抛异常
    → 没有 '中间件 返回', 因为异常直接往上冒了
```

**这条很重要**：如果你想"无论成功失败都记录一条日志"，必须用 `try/finally`：

```python
@app.middleware("http")
async def mw(request, call_next):
    try:
        return await call_next(request)
    finally:
        # 这里一定会执行
        ...
```

### 2.3.4 中间件能拿到什么

| 对象 | 有什么 |
| --- | --- |
| `request.method` | `GET` / `POST` |
| `request.url.path` | `/users/1` |
| `request.headers` | 请求头（大小写不敏感） |
| `request.state` | 一个空对象，中间件往里塞值，路由/依赖可以读 |
| `response.status_code` | 状态码 |
| `response.headers` | 响应头，可读可写 |

## 2.4 三个常用中间件

### 2.4.1 请求 id 透传

**为什么需要**：线上排查问题时，一个请求会在网关、应用、数据库留下多条日志，没有统一 id 就串不起来。

```python
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
    request.state.request_id = request_id
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response
```

三件事：**取或生成 → 存进 state → 写回响应头**。

案例文件：`fastapi_notes/ch02/code/02_request_id.py`

```plain
--- ① 客户端没带 id: 服务端自己生成 ---
    响应头 X-Request-ID -> 730259ab2253
    响应体里的 id       -> 730259ab2253

--- ② 客户端带了 id: 复用客户端的 ---
    响应头 X-Request-ID -> client-abc-123

--- ③ 两次请求的 id 不一样 ---
    相同吗: False (应该不同)
```

**为什么是 `uuid4().hex[:12]`**：完整 uuid 是 36 字符，日志里太占地方；12 位十六进制对单机排障足够。

### 2.4.2 耗时统计

```python
@app.middleware("http")
async def add_timing(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    cost_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Process-Time"] = f"{cost_ms:.1f}ms"
    if cost_ms > SLOW_THRESHOLD_MS:
        logger.warning("慢请求 %s %s %.1fms", request.method, request.url.path, cost_ms)
    return response
```

案例文件：`fastapi_notes/ch02/code/03_timing.py`

```plain
--- ① 快速接口: 响应头带耗时 ---
    X-Process-Time -> 0.8ms
    慢请求记录数   -> 0

--- ② 慢接口: 会被记进慢请求清单 ---
    X-Process-Time -> 300.7ms
    慢请求记录数   -> 1
    记录内容       -> ['GET /slow 300.7ms']
```

**为什么用 `perf_counter` 不用 `time.time()`**：`time.time()` 会被系统时钟校准（NTP）影响，可能算出负数；`perf_counter()` 单调递增，专门测间隔。

### 2.4.3 CORS

**先搞清楚它解决什么**：浏览器有"同源策略"。

```plain
   页面在 http://localhost:3000
   请求 http://127.0.0.1:8000
   端口不同 -> 不同源 -> 浏览器默认不让前端读响应
```

注意：**是浏览器在拦，不是服务端**。用 curl / Postman 调同一个接口完全正常。

配置：

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_methods=["*"],
    allow_headers=["*"],
    allow_credentials=True,
    max_age=600,
)
```

| 参数 | 含义 |
| --- | --- |
| `allow_origins` | 允许哪些来源（`*` 表示全部，但不建议） |
| `allow_methods` | 允许的 HTTP 方法 |
| `allow_headers` | 允许客户端带哪些自定义头 |
| `allow_credentials` | 允许带 cookie（此时 `allow_origins` 不能是 `*`） |
| `max_age` | 预检结果缓存多少秒，减少 OPTIONS 请求 |

案例文件：`fastapi_notes/ch02/code/04_cors.py`

```plain
--- ① 不加 CORS ---
    预检 OPTIONS 状态码 -> 405
    Access-Control-Allow-Origin -> None

--- ② 加了 CORS ---
    预检 OPTIONS 状态码 -> 200
    Access-Control-Allow-Origin  -> http://localhost:3000
    Access-Control-Allow-Methods -> DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT, QUERY
    Access-Control-Max-Age       -> 600

--- ④ 不在白名单的来源会被拒绝 ---
    状态码 -> 200 (接口本身还是 200)
    Access-Control-Allow-Origin -> None
    → 没有这个头, 浏览器就会拦住响应, 前端拿不到数据
```

最后一条最容易被误解：**接口返回 200 了，但前端还是拿不到数据**——因为浏览器看到没有 `Access-Control-Allow-Origin` 头，就不把响应交给 JS。

## 2.5 多个中间件的顺序

多个中间件是**洋葱式嵌套**：后注册的在更外层。

```python
@app.middleware("http")
async def a(request, call_next): ...     # 先注册

@app.middleware("http")
async def b(request, call_next): ...     # 后注册 -> 更外层
```

案例文件：`fastapi_notes/ch02/code/05_order_and_pitfall.py`

```plain
--- ① 三个中间件的执行顺序(洋葱模型) ---
      1. B 进入
      2. A 进入
      3. 路由函数
      4. A 返回
      5. B 返回
    → 注册顺序是 A、B、boom, 执行顺序是 boom -> B -> A
      后注册的在更外层, 所以 B 比 A 先进入
    → 返回时反过来(洋葱从里往外剥)
```

**实用建议**：需要"最早执行、最后退出"的中间件（比如请求 id、计时）应该**最后注册**。

## 2.6 两个坑

### 2.6.1 中间件抛的异常，不会被 `exception_handler` 捕获

```plain
--- ② 路由抛 AppError: 被 exception_handler 接住 -> 404 ---
    状态码: 404  响应: {'detail': '用户不存在'}

--- ③ 中间件抛异常: 不会被 exception_handler 接住 ---
    状态码: 500 (变成 500 了)
    → 日志里没有'异常处理器接住', 说明它根本没被调用
```

**原因**：异常处理器在中间件的**内层**。异常从中间件抛出时，已经越过了那一层。

所以中间件里的代码要自己兜底：

```python
@app.middleware("http")
async def mw(request, call_next):
    try:
        return await call_next(request)
    except Exception:
        logger.exception("中间件出错")
        raise
```

### 2.6.2 不要在中间件里做重活

中间件对**所有请求**生效，包括静态文件、健康检查、404。如果在里面查数据库、调外部接口，会把每个请求都拖慢。

| 该放中间件 | 该放依赖或路由 |
| --- | --- |
| 记日志、加响应头 | 查数据库 |
| 计时、请求 id | 业务校验 |
| CORS | 权限判断（要拿用户信息） |

## 2.7 在项目里落地

### 2.7.1 新增 `project/app/core/middleware.py`

一个中间件同时做请求 id 和耗时统计（两件事都要在 `call_next` 前后各写一段，合在一起更省事）：

```python
def register_middlewares(app: FastAPI) -> None:
    @app.middleware("http")
    async def request_context(request: Request, call_next):
        request_id = request.headers.get(REQUEST_ID_HEADER) or uuid.uuid4().hex[:12]
        request.state.request_id = request_id
        start = time.perf_counter()

        response = await call_next(request)

        cost_ms = (time.perf_counter() - start) * 1000
        response.headers[REQUEST_ID_HEADER] = request_id
        response.headers[PROCESS_TIME_HEADER] = f"{cost_ms:.1f}ms"

        if cost_ms > SLOW_THRESHOLD_MS:
            logger.warning("慢请求 %s %s %.1fms request_id=%s", ...)

        return response
```

### 2.7.2 在 `main.py` 挂上

```python
app = FastAPI(title=settings.app_name, version="0.1.0", lifespan=lifespan)

register_middlewares(app)        # 在注册路由之前

app.include_router(health.router)
...
```

## 2.8 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 中间件里 `await call_next` 报 `RuntimeError` | 写成了同步 `def` 但没 `await` | 中间件必须是 `async def`，并 `await call_next(request)` |
| 中间件抛异常后业务异常处理器没生效 | 异常处理器在内层 | 中间件里自己 `try/except` |
| 加了中间件后所有接口变慢 | 中间件里做了查库/网络调用 | 重活放路由或依赖里 |
| CORS 配了但前端还是跨域 | `allow_origins` 写的是前端地址，实际是别的端口 | 看浏览器 Network 里的 `Origin` 头，逐字比对 |
| `allow_credentials=True` 时带 `*` 报错 | 规范不允许 | 明确列出域名 |
| 加了响应头的代码不执行 | 路由抛异常，`call_next` 之后的代码被跳过 | 用 `try/finally` |
| 中间件顺序不对 | 以为"先注册先执行" | 后注册的在**外层**，先执行 |

## 2.9 本章小结

1. 中间件包住所有请求，`await call_next(request)` 之前是请求阶段、之后是响应阶段。
2. 中间件拿不到路由参数，也不该做业务判断——那是依赖的活。
3. 路由抛异常时，`call_next` 之后的代码不会执行，要记日志就用 `try/finally`。
4. 三个常用能力：请求 id（取或生成 + 回写响应头）、耗时统计（`perf_counter`）、CORS（浏览器同源策略）。
5. CORS 是**浏览器**在拦，接口返回 200 不代表前端能拿到数据，要看有没有 `Access-Control-Allow-Origin`。
6. 多个中间件是洋葱模型：后注册的在外层、先进入、后退出。
7. 中间件里抛的异常**不会**被 `@app.exception_handler` 捕获，要自己兜底。
8. 项目已接入 `request_context` 中间件，并补了 5 个测试。
