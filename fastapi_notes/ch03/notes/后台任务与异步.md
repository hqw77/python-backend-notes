# FastAPI 第三章 · 后台任务与异步

## 3.1 学习目标

这一章解决一个很实际的困惑：**为什么写了 `async def` 反而更慢**。学完应该能做到：

1. 说清 `async def` 和普通 `def` 在 FastAPI 里被怎么处理
2. 知道"async def 里写阻塞调用"为什么是最糟的组合
3. 能判断自己的代码该写哪种
4. 会用 `BackgroundTasks` 把非必要等待挪到响应之后
5. 知道什么时候该换 Celery

前置知识：第二章（中间件）、`mysql_notes` 第六章（路由）。

> **本章的读法**：三个案例都用真实并发请求测耗时，数字很直观。
> 最后一节把"注册后发欢迎通知"接进 `project/`。

## 3.2 async def 和 def 到底差在哪

### 3.2.1 先理解事件循环

异步框架（FastAPI / Starlette）内部是一个**事件循环**：单线程，靠"谁在等就让位"来同时处理很多请求。

```plain
   请求 A 进来 -> 开始处理 -> 遇到要等的地方(比如读网络)
                              │
                              ├─ 主动让出: "我先歇着, 你们继续"
                              ▼
   请求 B 进来 -> 开始处理 ...
                              │
   请求 A 的数据到了 -> 回到 A 继续
```

关键在于「**主动让出**」。只有写成 `await xxx` 的时候，程序才会让出控制权。

`time.sleep(1)` 不会让出——它就是**原地傻等 1 秒**，整个事件循环跟着停摆。

### 3.2.2 FastAPI 对两种函数的处理不一样

| 你写的 | FastAPI 怎么执行 | 会不会卡住别人 |
| --- | --- | --- |
| `async def` | 直接在事件循环里跑 | **会**，只要你写了阻塞代码 |
| 普通 `def` | 丢到线程池（默认 40 个线程） | 不会，线程池能并发 |

这条反直觉，但很重要：**普通 `def` 反而更安全**，因为它不在事件循环里。

### 3.2.3 最糟的组合

```python
@app.get("/bad")
async def bad():
    time.sleep(1)          # ← async def 里写同步阻塞
    return {"ok": True}
```

后果：并发 10 个请求，总耗时 = 10 秒。CPU 不高，但所有接口一起变慢，而且很难查。

> **通俗理解**：事件循环像一个服务员，`await` 是"我去催菜，你先招呼别的桌"，`time.sleep` 是"我站在厨房门口死等，谁也别找我"。

## 3.3 实测：阻塞 vs 非阻塞

案例文件：`fastapi_notes/ch03/code/01_blocking_event_loop.py`

并发 5 个请求，每个 sleep 0.3 秒：

```plain
--- ① async def + time.sleep(阻塞) ---
    总耗时: 1.51 秒
    理论值: 1.50 秒 (5 个请求完全串行)

--- ② async def + await asyncio.sleep(非阻塞) ---
    总耗时: 0.31 秒
    理论值: 0.30 秒 (5 个请求真正并发)
```

**1.51 秒 vs 0.31 秒，差 5 倍**——正好是请求数。

### 3.3.1 换成普通 def 呢

案例文件：`fastapi_notes/ch03/code/02_def_in_threadpool.py`

同一个阻塞函数，分别用两种方式包装：

```plain
--- ① async def 包同步阻塞函数 ---
    总耗时: 1.51 秒

--- ② 普通 def 包同一个函数 ---
    总耗时: 0.32 秒
```

**同一个函数，`def` 比 `async def` 快 5 倍**。因为它被丢进了线程池。

## 3.4 怎么判断该写哪种

看**你调用的库是同步还是异步**：

| 你用的库 | 该写 | 例子 |
| --- | --- | --- |
| 异步库（都要 `await`） | `async def` | `httpx.AsyncClient`、`aiomysql`、`asyncpg`、`aiofiles` |
| 同步库（不用 await） | 普通 `def` | `requests`、`pymysql`、同步 `SQLAlchemy`、`time.sleep` |

**本项目的情况**：用的是同步 SQLAlchemy + PyMySQL，所以正确的写法是普通 `def`——现在 `project/` 里的路由就是普通 `def`，这是对的。

如果哪天换成了 `asyncpg` 或 `SQLAlchemy` 的异步模式，就要把整条链路都改成 `async def + await`。

### 3.4.1 一个必须避开的写法

```python
# ❌ 最糟：async def 里跑同步阻塞
@app.get("/x")
async def x():
    requests.get("https://example.com")     # 卡住整个服务
    return {}
```

两种改法，任选其一：

```python
# ✅ 改法一：改成普通 def，交给线程池
@app.get("/x")
def x():
    requests.get("https://example.com")
    return {}

# ✅ 改法二：留在 async def，但换成异步库
@app.get("/x")
async def x():
    async with httpx.AsyncClient() as client:
        await client.get("https://example.com")
    return {}
```

## 3.5 BackgroundTasks：让用户不用等

### 3.5.1 场景

注册成功后要发一封欢迎邮件。邮件服务器可能要 0.5~2 秒，但这跟用户无关——**用户只想尽快看到"注册成功"**。

```python
@app.post("/register")
def register(background: BackgroundTasks):
    # ... 创建用户 ...
    background.add_task(send_welcome_email, "x@example.com")
    return user          # 立刻返回
```

`add_task(函数, *参数)`：把函数和参数排进队列，**响应发出去之后**才执行。

### 3.5.2 实测

案例文件：`fastapi_notes/ch03/code/03_background_tasks.py`

```plain
--- ① 同步发邮件: 路由要等邮件发完 ---
    路由内耗时: 0.3 秒

--- ② 后台发邮件: 路由立刻返回 ---
    路由内耗时: 0.0 秒
    邮件发了吗: ['b@example.com'] (响应之后才发)
```

**用户感知的延迟从 0.3 秒降到接近 0**。

### 3.5.3 坑：后台任务的异常会被吞掉

```plain
--- ④ 后台任务失败了会怎样 ---
    响应状态码: 200  响应体: {'msg': '接口正常返回'}
    → 异常只出现在服务端日志里, 客户端完全不知道
    → 后台任务的异常不会影响响应, 也不会自动重试
```

所以**后台任务函数里必须自己 `try/except` + 打日志**，否则出错了没人知道。

```python
def send_welcome_notice(username: str) -> None:
    try:
        ...
    except Exception:
        logger.exception("发送欢迎通知失败: %s", username)
```

### 3.5.4 BackgroundTasks 的局限

| 局限 | 说明 |
| --- | --- |
| **进程内** | 进程重启/崩溃，没跑完的任务直接丢 |
| **没有重试** | 失败就是失败 |
| **没有队列** | 任务多了全压在同一个进程里 |
| **看不到状态** | 无法查询"任务跑到哪了" |

**只适合"丢了也不致命"的事**：发通知、写日志、清临时文件、埋点上报。

## 3.6 什么时候该换 Celery / RQ

| 需求 | BackgroundTasks 够吗 | 建议 |
| --- | --- | --- |
| 发个通知，丢了就丢了 | ✅ 够 | 继续用 |
| 任务要重试（比如支付回调） | ❌ | 换 Celery |
| 任务要跑几分钟（生成报表） | ❌ | 换 Celery |
| 要能查任务状态 | ❌ | 换 Celery + 结果后端 |
| 任务量很大要扩机器 | ❌ | 换 Celery + 多 worker |

判断方法：**问自己"这个任务失败了，能接受吗"**。能接受 → BackgroundTasks；不能 → 队列。

> **通俗理解**：`BackgroundTasks` 是"我出门顺手把垃圾带下去"，忘带就忘带了；Celery 是"叫了个快递，系统会一直跟进直到送达"。

## 3.7 在项目里落地

### 3.7.1 新增 `app/services/notify_service.py`

```python
def send_welcome_notice(username: str) -> None:
    try:
        logger.info("发送欢迎通知给 %s", username)
    except Exception:
        logger.exception("发送欢迎通知失败: %s", username)
```

真实项目这里会调 SMTP 或第三方 API——那一步往往几百毫秒，正是该放后台的。

### 3.7.2 注册接口挂上

```python
@router.post("/register", response_model=UserOut, status_code=201)
def register(
    payload: RegisterIn,
    background: BackgroundTasks,
    db: Session = Depends(get_db),
) -> UserOut:
    user = auth_service.register(db, payload.username, payload.phone, payload.password)
    background.add_task(notify_service.send_welcome_notice, user.username)
    return user
```

注意用的是 `notify_service.send_welcome_notice`（模块属性），不是 `from ... import send_welcome_notice`——这样测试里才能用 `monkeypatch` 替换掉。

## 3.8 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 并发一高所有接口都变慢 | `async def` 里写了同步阻塞调用 | 改成普通 `def`，或换异步库 |
| 改了 `async def` 反而更慢 | 同上 | 检查里面的调用是不是同步的 |
| 后台任务没执行 | 只 `import` 了函数没调用 `add_task` | 检查是否真的 `background.add_task(...)` |
| 后台任务报错但接口正常 | 异常被静默吞掉 | 任务函数里自己 `try/except` + 日志 |
| 服务重启后任务丢了 | `BackgroundTasks` 不持久化 | 换成 Celery / RQ |
| `TypeError: add_task() takes ...` | 参数传错，要 `add_task(函数, 参数1, 参数2)` | 用位置参数，不要写成 `add_task(f(a))` |
| `async def` 里用 `requests` | 同步库 | 改 `httpx.AsyncClient` 或改回普通 `def` |

## 3.9 本章小结

1. FastAPI 把 `async def` 放在事件循环里、普通 `def` 丢线程池。
2. **最糟的组合是 `async def` + 同步阻塞调用**：实测 5 个并发请求从 0.31 秒变成 1.51 秒。
3. 同一个阻塞函数，用普通 `def` 反而快 5 倍（0.32 秒 vs 1.51 秒），因为走了线程池。
4. 判断标准：调用的是异步库就 `async def`，是同步库就普通 `def`。
5. 本项目用同步 SQLAlchemy，所以路由写普通 `def` 是对的。
6. `BackgroundTasks` 把非必要等待挪到响应之后，用户感知延迟从 0.3 秒降到接近 0。
7. 后台任务的异常**不会**影响响应，也不会重试——必须自己兜底。
8. 任务需要重试/持久化/可查状态时，换 Celery。
