## 1.2 回顾：Depends 在做什么

普通写法：参数自己声明，校验自己写。

```python
@app.get("/items")
def list_items(page: int = 1, size: int = 10):
    offset = (page - 1) * size
    ...
```

用依赖：把"准备这个值"的动作抽出去。

```python
def pagination(page: int = 1, size: int = 10) -> dict:
    return {"page": page, "size": size, "offset": (page - 1) * size}

@app.get("/items")
def list_items(p: dict = Depends(pagination)):
    ...
```

FastAPI 在调用路由函数之前，先执行 `pagination()`，把返回的字典塞进 `p`。

### 1.2.1 三个"顺带的好处"

| 好处 | 说明 |
| --- | --- |
| **参数自动提升** | 依赖函数里的 `page`、`size` 会自动变成接口的查询参数，不用在路由里重复声明 |
| **校验自动生效** | 依赖里写 `Query(ge=1)`，路由里一样会被校验 |
| **文档自动生成** | `/docs` 里能看到这些参数，不用手写 |

案例文件：`fastapi_notes/ch01/code/01_depends_basic.py`

```plain
--- ① 用依赖的分页接口: 默认值 ---
    GET /items          -> {'分页参数': {'page': 1, 'size': 10, 'offset': 0}}

--- ② 依赖函数的参数会自动变成查询参数 ---
    GET /items?page=2&size=5 -> {'分页参数': {'page': 2, 'size': 5, 'offset': 5}}

--- ⑤ 打开文档会看到什么 ---
    /items 的查询参数: ['page', 'size']
    → 依赖里的参数自动出现在接口文档里, 不用手写
```

> **通俗理解**：`Depends` 像"点菜前的备菜"——你说"我要一份分页"，厨房（依赖）自己把 page、size、offset 都配好端上来，你只管炒（写业务逻辑）。

## 1.3 依赖缓存：一个请求只执行一次

### 1.3.1 现象

如果两个参数依赖同一个函数：

```python
@app.get("/cached")
def use_twice(
    a: dict = Depends(expensive_dep),
    b: dict = Depends(expensive_dep),
):
    ...
```

FastAPI **只执行一次** `expensive_dep()`，`a` 和 `b` 拿到的是同一个对象。

案例文件：`fastapi_notes/ch01/code/02_depends_cache.py`

```plain
--- ① 默认开启缓存: 一个请求里用两次, 只执行一次 ---
    返回: {'a': {'value': '查了一次库', 'calls': 1}, 'b': {'value': '查了一次库', 'calls': 1},
           '依赖执行次数': 1}

--- ② 用三次也只执行一次 ---
    返回: {'执行次数': 1}
```

### 1.3.2 为什么这很重要

假设 `get_current_user` 里要查一次数据库。一个接口里如果同时用到：

- `Depends(get_current_user)`
- `Depends(require_role("admin"))`（内部也依赖 `get_current_user`）

没有缓存就要查两次库；有缓存只查一次。

### 1.3.3 缓存的范围：只在同一个请求内

```plain
--- ④ 缓存的作用范围: 只在同一个请求内 ---
    连续请求两次, 依赖总执行次数: 2
```

每次请求重新开始，不会跨请求复用——否则用户信息会一直停在上一次。

### 1.3.4 怎么关掉

```python
Depends(expensive_dep, use_cache=False)
```

```plain
--- ③ 关掉缓存: 每处各执行一次 ---
    返回: {'a': {... 'calls': 1}, 'b': {... 'calls': 2}, '依赖执行次数': 2}
```

| 场景 | 该不该关 |
| --- | --- |
| 依赖只读数据（查用户、读配置） | 不用关，缓存更快 |
| 依赖有副作用（写库、发消息） | **要关**，否则只执行一次 |
| 依赖每次要拿最新值 | 要关 |

> **通俗理解**：缓存像"这一单里同一个菜只做一次，两份都端这一锅"。如果每次都要现炒（有副作用），就得说"别复用，另起一锅"。

## 1.4 子依赖：依赖里还能依赖

### 1.4.1 三层鉴权

真实项目的鉴权是链式的：

```plain
   get_user_id          从请求头解析出用户 id
        │
        ▼
   get_current_user     用 id 查用户
        │
        ▼
   require_admin        检查角色
        │
        ▼
   路由函数
```

每一层都是独立的依赖，后一层把前一层当参数：

```python
def get_user_id(authorization: str = Header(default="")) -> int:
    token = authorization.replace("Bearer ", "")
    if token not in TOKENS:
        raise HTTPException(status_code=401, detail="令牌无效")
    return TOKENS[token]


def get_current_user(user_id: int = Depends(get_user_id)) -> dict:
    user = USERS.get(user_id)
    if user is None:
        raise HTTPException(status_code=401, detail="用户不存在")
    return user


def require_admin(user: dict = Depends(get_current_user)) -> dict:
    if "admin" not in user["roles"]:
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return user
```

### 1.4.2 跑一遍

案例文件：`fastapi_notes/ch01/code/03_sub_dependency.py`

```plain
--- ① 没带令牌 -> 第 1 层就拦下(401) ---
    GET /profile           -> 401 {'detail': '令牌无效'}

--- ② 带普通用户令牌 -> 第 2 层通过 ---
    GET /profile           -> 200 {'用户名': '李四', '角色': ['viewer']}

--- ③ 普通用户访问管理员接口 -> 第 3 层拦下(403) ---
    GET /admin/users       -> 403 {'detail': '需要管理员权限'}

--- ④ 管理员令牌 -> 三层全过 ---
    GET /admin/users       -> 200 {'操作人': '张三', ...}
```

**任何一层抛异常，后面的都不执行**——这就是依赖链的短路效果。

### 1.4.3 和项目里的实现对照

`project/app/deps.py` 里的 `get_current_user` 和 `require_role` 就是这个结构：

```python
def get_current_user(credentials=Depends(bearer_scheme), db=Depends(get_db)) -> User: ...
def require_role(*role_names): 
    def checker(current_user: User = Depends(get_current_user)) -> User: ...
    return checker
```

`require_role` 之所以返回一个函数，是因为它要在"依赖"里再包一层参数（要什么角色）。

> **通俗理解**：子依赖像"流水线"——上一道工序的产物交给下一道。令牌解析出 id，id 交给查用户，用户交给查角色。任何一道不合格，产品直接下线（返回错误）。

## 1.5 类作为依赖：把一组参数打包

### 1.5.1 为什么需要

列表接口经常要这三个参数：

```python
def list_users(
    page: int = Query(1, ge=1),
    size: int = Query(10, ge=1, le=100),
):
    offset = (page - 1) * size
```

每个列表接口都写一遍，改规则要改 N 处。

### 1.5.2 用类包装

```python
class Pagination:
    def __init__(
        self,
        page: int = Query(1, ge=1, description="页码"),
        size: int = Query(10, ge=1, le=100, description="每页条数"),
    ) -> None:
        self.page = page
        self.size = size
        self.offset = (page - 1) * size


@app.get("/items")
def list_items(p: Pagination = Depends()):
    return {"page": p.page, "size": p.size, "offset": p.offset}
```

两个要点：

1. FastAPI 会解析 `__init__` 的参数，当成查询参数；
2. `Depends()` **不写参数**时，类型注解 `Pagination` 就是依赖本身。

案例文件：`fastapi_notes/ch01/code/04_class_and_yield.py`

```plain
--- ① 类依赖: 一组参数变成一个对象 ---
    GET /items                 -> {'page': 1, 'size': 10, 'offset': 0}
    GET /items?page=3&size=20  -> {'page': 3, 'size': 20, 'offset': 40}

--- ② 类依赖也继承了 Query 的校验 ---
    GET /items?size=999        -> 422 Input should be less than or equal to 100
```

## 1.6 yield 依赖：前半段准备，后半段清理

### 1.6.1 写法

```python
def get_session():
    session = FakeSession()      # yield 之前: 准备资源
    try:
        yield session            # 交给路由函数用
    finally:
        session.close()          # yield 之后: 清理
```

### 1.6.2 清理一定会执行

```plain
--- ③ yield 依赖: 正常请求的执行顺序 ---
    执行顺序: 打开连接 -> 执行路由函数 -> 关闭连接

--- ④ 路由抛异常时, yield 后面的清理照样执行 ---
    执行顺序: 打开连接 -> 路由抛异常 -> 关闭连接
```

即使路由函数抛了异常，`finally` 里的 `close()` 也会执行——这就是 `project/app/db/session.py` 里 `get_db` 能保证"连接一定归还"的原因。

### 1.6.3 和普通 return 依赖的区别

| | `return` 依赖 | `yield` 依赖 |
| --- | --- | --- |
| 执行次数 | 只在请求前执行 | 请求前后各执行一段 |
| 能清理资源吗 | 不能 | 能（`finally`） |
| 适用 | 解析 token、算分页 | 数据库 Session、文件句柄、临时目录 |

> **通俗理解**：`return` 依赖像"递给你一把钥匙就完事"；`yield` 依赖像"租车"——交车、你用、还车，还车这一步不管你出没出事故都会做。

## 1.7 在项目里落地

### 1.7.1 改造前

`project/app/routers/users.py`：

```python
@router.get("", response_model=UserPage)
def list_users(
    page: int = Query(1, ge=1, description="页码,从 1 开始"),
    size: int = Query(10, ge=1, le=100, description="每页条数,最大 100"),
    db: Session = Depends(get_db),
) -> UserPage:
    items, total = user_service.list_users(db, page=page, size=size)
    return UserPage(total=total, page=page, size=size, items=items)
```

### 1.7.2 改造后

新增 `project/app/core/pagination.py`：

```python
class PageParams:
    def __init__(
        self,
        page: int = Query(1, ge=1, description="页码,从 1 开始"),
        size: int = Query(10, ge=1, le=100, description="每页条数,最大 100"),
    ) -> None:
        self.page = page
        self.size = size
        self.offset = (page - 1) * size
```

路由变成：

```python
@router.get("", response_model=UserPage)
def list_users(p: PageParams = Depends(), db: Session = Depends(get_db)) -> UserPage:
    items, total = user_service.list_users(db, page=p.page, size=p.size)
    return UserPage(total=total, page=p.page, size=p.size, items=items)
```

### 1.7.3 收益

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 路由参数 | 3 个 | 2 个 |
| 分页规则写在哪 | 每个列表接口 | 只有 `pagination.py` 一处 |
| 以后加分页字段（如排序） | 所有接口都改 | 只改类 |

### 1.7.4 验证

接口文档里的参数没变：

```plain
['page', 'size']
```

测试也补了 4 个：

```plain
17 passed
```

| 用例 | 验证 |
| --- | --- |
| `test_list_users_default_page` | 默认第 1 页、每页 10 条 |
| `test_list_users_custom_page` | `?page=2&size=2` 生效 |

## 1.8 依赖覆盖（提前了解）

测试时经常要把真依赖换成假的，比如把"真数据库"换成"内存库"：

```python
app.dependency_overrides[get_db] = lambda: fake_db
```

原理是 FastAPI 内部维护一张"依赖 -> 提供者"的表，测试时可以替换。这部分细节放在第七章（测试进阶），现在知道有这么个东西就行。

## 1.9 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 依赖里的参数没出现在文档里 | 依赖写成 `def dep()` 但没在路由用 `Depends(dep)` | 检查路由参数是否真的挂了依赖 |
| 依赖执行了两次 | 两处都写了 `use_cache=False`，或依赖有副作用 | 保持默认，让缓存生效 |
| 自定义类依赖报 `TypeError: __init__() takes 1 positional argument` | 路由写成 `Depends(Pagination)` 而不是 `Depends()` | 类依赖用 `Depends()`，类型注解写类名 |
| `yield` 依赖报 `AttributeError: 'generator' object has no attribute ...` | 用了 `yield` 但路由参数类型写错 | 依赖函数必须 `yield` 一个值，路由参数类型要对上 |
| 清理代码没执行 | 没用 `try/finally`，异常时跳过 | 包在 `try` 里，清理写 `finally` |
| 依赖里抛 `HTTPException` 后路由还执行了 | 检查是否真的在依赖里 | 抛出即中断，路由不会执行 |

## 1.10 本章小结

1. `Depends` 在路由函数前执行，把返回值注入参数；依赖里的参数会自动变成查询参数并参与校验。
2. **依赖缓存**（`use_cache=True` 默认）：一个请求内同一个依赖只执行一次，跨请求不缓存。
3. 依赖有副作用时要 `use_cache=False`。
4. **子依赖**让鉴权可以分层：解析令牌 → 查用户 → 查角色，任意一层失败立即中断。
5. **类依赖**把一组参数打包，`Depends()` 不写参数、用类型注解指定。
6. **`yield` 依赖**在请求后做清理，异常时也会执行，是管 Session 的标准写法。
7. 项目里已用 `PageParams` 替换了重复的分页参数，规则收敛到一处。
