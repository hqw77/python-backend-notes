# FastAPI 第五章 · 可观测性

## 5.1 学习目标

服务上线后，出问题时你只有日志。这一章讲怎么让日志**能查、能串、能定位**：

1. 说清一条有用的日志该包含什么
2. 会配置格式化的日志输出
3. 理解为什么 `request_id` 要用 `contextvar` 而不是全局变量
4. 知道日志级别怎么选
5. 能把日志接进项目，让业务日志自动带上请求 id

前置知识：第二章（中间件、`X-Request-ID`）。

---

## 5.2 一条好日志要有什么

```plain
❌ INFO:root:发送欢迎通知给 张三

✅ 2026-11-10 20:56:35,613 INFO [e2c549b804d0] app.notify: 发送欢迎通知给 张三
   └── 时间 ────────┘ └级别┘ └─ 请求 id ─┘ └─ 模块 ─┘ └── 内容 ──┘
```

三个要素对应三个问题：

| 要素 | 回答什么 |
| --- | --- |
| 时间戳 | 什么时候发生的 |
| `request_id` | 是**哪一个请求**的 |
| logger 名字 | 哪个模块打的 |

缺了 `request_id`，一个请求打出的 5 条日志就是 5 条孤立的记录，没法串成一条链路。

---

## 5.3 三种配置对比

案例文件：`fastapi_notes/ch05/code/01_logging_basics.py`

### 5.3.1 默认配置

```python
logging.getLogger("demo.default").warning("发送欢迎通知给 张三")
```

```plain
发送欢迎通知给 张三
```

只有消息。没有时间、没有模块名、没有请求上下文。

### 5.3.2 自定义格式

```python
handler.setFormatter(logging.Formatter(
    "%(asctime)s %(levelname)-7s %(name)s: %(message)s"
))
```

```plain
2026-11-10 20:56:12,613 INFO    demo.simple: 发送欢迎通知给 张三
2026-11-10 20:56:12,613 WARNING demo.simple: 慢请求 GET /users 320.5ms
```

`%(levelname)-7s` 里的 `-7` 是左对齐补空格，让 INFO / WARNING 的冒号能对齐——小细节，但让日志好扫。

### 5.3.3 加上请求 id

```python
handler.setFormatter(logging.Formatter(
    "%(asctime)s %(levelname)-7s [%(request_id)s] %(name)s: %(message)s"
))
```

```plain
2026-11-10 20:56:12,613 INFO    [-] demo.trace: 没有请求上下文时, request_id 是默认值
2026-11-10 20:56:12,613 INFO    [a1b2c3d4e5f6] demo.trace: 在请求里, request_id 自动带上
2026-11-10 20:56:12,613 WARNING [a1b2c3d4e5f6] demo.trace: 这条慢请求日志也能串起来了
2026-11-10 20:56:12,613 INFO    [-] demo.trace: 退出请求后, 又回到默认值
```

`[-]` 表示"不在请求里"（比如启动阶段、定时任务）。

## 5.4 为什么用 contextvar 而不是全局变量

### 5.4.1 全局变量会串号

```python
GLOBAL_ID = {"value": "-"}

async def handle(name):
    GLOBAL_ID["value"] = name        # 先写
    await asyncio.sleep(delay)       # 模拟查库
    return GLOBAL_ID["value"]        # 再读
```

案例文件：`fastapi_notes/ch05/code/02_contextvar.py`

```plain
--- ① 用全局变量(会串号) ---
    req-A 读到的 id = req-C
    req-B 读到的 id = req-C
    req-C 读到的 id = req-C

--- ② 用 contextvar(互不干扰) ---
    req-A 读到的 id = req-A
    req-B 读到的 id = req-B
    req-C 读到的 id = req-C
```

**并发下全局变量只有一份**，谁最后写就是谁——A 和 B 的日志都会带上 C 的 id，排查时会被带偏。

### 5.4.2 contextvar 怎么做

```python
from contextvars import ContextVar

request_id_ctx: ContextVar[str] = ContextVar("request_id", default="-")

request_id_ctx.set("abc123")     # 设置
request_id_ctx.get()             # 读取
request_id_ctx.reset(token)      # 恢复
```

| | 全局变量 | contextvar |
| --- | --- | --- |
| 存几份 | 全进程一份 | 每个 task/协程一份 |
| 并发安全 | ❌ | ✅ |
| 适合 | 进程级配置 | 请求级上下文 |

> **通俗理解**：全局变量像一块公共白板，谁都能写，最后一个人覆盖所有人；contextvar 像每人手里一张便签，互不影响。

## 5.5 在项目里落地

### 5.5.1 新增 `app/core/logging.py`

三个部分：

```python
request_id_ctx: ContextVar[str] = ContextVar("request_id", default="-")

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id_ctx.get()    # 每条日志自动补字段
        return True

def setup_logging(level=logging.INFO) -> None:
    ...
```

`setup_logging` 用标记位去重，重复调用不会加两个 handler（否则日志会打两遍）。

### 5.5.2 中间件里 set / reset

```python
token = request_id_ctx.set(request_id)
try:
    response = await call_next(request)
    ...
    return response
finally:
    request_id_ctx.reset(token)      # 一定要重置
```

**为什么必须 reset**：中间件是复用的，不重置的话，下一个请求可能读到上一个请求残留的值。

### 5.5.3 `main.py` 里调用

```python
setup_logging()

app = FastAPI(...)
```

### 5.5.4 效果

注册接口的日志：

```plain
2026-11-10 20:56:35,613 INFO [e2c549b804d0] app.notify: 发送欢迎通知给 logdemo2
register: 201 | request id: e2c549b804d0
```

**日志里的 id 和响应头 `X-Request-ID` 完全一致**——用户报障时报这个 id，你就能把所有相关日志捞出来。

### 5.5.5 顺带压掉第三方噪声

```python
for noisy in ("httpx", "httpcore", "urllib3"):
    logging.getLogger(noisy).setLevel(logging.WARNING)
```

不加这行，每发一次 HTTP 请求 httpx 就打一条 INFO，日志会被冲垮。

## 5.6 日志级别怎么用

| 级别 | 什么时候用 | 例子 |
| --- | --- | --- |
| `DEBUG` | 只在开发时看 | 变量值、SQL 参数 |
| `INFO` | 正常的重要事件 | 用户注册成功、任务开始 |
| `WARNING` | 不正常但不影响功能 | 慢请求、重试了一次 |
| `ERROR` | 功能出错但还能跑 | 发通知失败、外部接口超时 |
| `CRITICAL` | 服务不可用 | 数据库连不上 |

**常见错误**：把"用户注册成功"打成 `WARNING`，或者把"数据库连不上"打成 `INFO`。级别决定了告警规则，打错等于告警失效。

> **通俗理解**：级别像医院的检伤分类——不是按你多紧张，是按"要不要立刻处理"。

## 5.7 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 日志打两遍 | `setup_logging` 被调用多次 | 用标记位去重 |
| 日志里没有 request_id | 没加 `RequestIdFilter`，或中间件没 set | 检查两处都配了 |
| 并发时 request_id 乱串 | 用了全局变量 | 改成 `ContextVar` |
| 日志没有输出 | `propagate = False` 但没加 handler | 检查 logger 配置 |
| 第三方库日志刷屏 | 根 logger 级别太低 | 单独调高 httpx 等的级别 |
| 线上日志找不到某请求 | 没把 `X-Request-ID` 返回给前端 | 中间件里加到响应头 |

## 5.8 本章小结

1. 有用的日志要能回答三个问题：什么时候、哪个请求、哪个模块。
2. `request_id` 要贯穿：中间件生成 → 响应头返回 → 日志里带上。
3. **并发场景必须用 `ContextVar`**，全局变量会串号（实测 A、B 都读到了 C 的 id）。
4. `logging.Filter` 可以把 contextvar 的值自动塞进每条日志，业务代码不用手写。
5. `setup_logging` 要去重，否则日志打两遍。
6. 按"要不要立刻处理"选级别，别把 ERROR 打成 INFO。
7. 项目已接入：日志格式带 `[request_id]`，且与响应头一致。

## 5.9 练习

1. 把日志格式改成 JSON（每行一个 `{"ts":..., "level":..., "request_id":..., "msg":...}`），说明为什么结构化日志更适合接日志平台。
2. 给 `setup_logging` 加一个"是否输出到文件"的参数，按天切分文件。
3. 写一个测试：注册接口成功后，捕获日志并断言里面包含该请求的 `request_id`。
4. 思考：如果 `reset(token)` 忘了写，会出现什么现象？怎么用测试暴露它？
