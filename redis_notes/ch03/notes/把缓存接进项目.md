# Redis 第三章 · 把缓存接进项目

## 3.1 学习目标

前两章都是独立脚本，这一章把缓存真正接进 `project/`，改动真实代码。学完应该能做到：

1. 说清缓存应该加在哪一层、为什么不在路由层加
2. 理解"缓存 DTO 而不是 ORM 对象"这个设计决策
3. 掌握读路径改造与写路径失效的落点
4. 能拿出数据：命中缓存后一条 SQL 都不发
5. 会用测试验证缓存行为（命中、失效、404 不缓存）

前置知识：第一章（命令）、第二章（Cache-Aside）、第七章（service 分层）。

> **本章的读法**：先看"改了哪 5 个文件"，再看读路径与写路径两段代码，最后跑案例验证。
> 案例会直接调用真实接口，需要 MySQL 和 Redis 都在运行。

## 3.2 改造前的结构

回忆第七章的分层：

```plain
   请求
    │
    ▼
routers/users.py        get_user()  ->  user_service.get_user(db, id)
    │
    ▼
services/user_service.py  查库, 查不到抛 404
    │
    ▼
models/user.py -> MySQL
```

现在要在"路由"和"service"之间插一层缓存。

## 3.3 落点：改了 5 个文件

| 文件 | 动作 | 作用 |
| --- | --- | --- |
| `app/core/config.py` | 改 | 加 6 项 Redis 配置 |
| `app/db/redis_client.py` | 新建 | 连接池 + 客户端 |
| `app/services/cache.py` | 新建 | JSON 读写 + key 命名 + 默认 TTL |
| `app/services/user_cache.py` | 新建 | 用户详情的 Cache-Aside |
| `app/services/user_service.py` | 改 | 写操作后删缓存 |
| `app/routers/users.py` | 改 | 详情接口改走缓存 |
| `app/main.py` | 改 | 关闭时释放 Redis 连接 |
| `tests/test_cache.py` | 新建 | 5 个缓存用例 |

**为什么不在路由层直接写 Redis？**

路由层的职责是"收参数、返响应"。如果在那里写 `redis_client.get()`，会有三个问题：

1. 别的入口（定时任务、命令行工具）想用同一份数据，得复制一遍缓存逻辑
2. `get_db` 和 Redis 客户端混在一起，测试时不好替换
3. key 的命名散落各处，改一次要全局搜

所以放在 service 层，路由只调一行。

## 3.4 两个新文件的职责

### 3.4.1 `db/redis_client.py`：连接池

```python
redis_pool = redis.ConnectionPool(
    host=settings.redis_host,
    port=settings.redis_port,
    db=settings.redis_db,
    password=settings.redis_password or None,
    decode_responses=True,
    max_connections=settings.redis_max_connections,
)

redis_client = redis.Redis(connection_pool=redis_pool)
```

和 `db/engine.py` 是一个套路：**全进程一个池子，各处借用**。

`decode_responses=True` 必须开，否则取出来是 `bytes`，`json.loads` 会报错。

### 3.4.2 `services/cache.py`：读写封装

```python
def user_key(user_id: int) -> str:
    return f"user:{user_id}"

def get_json(key: str):
    raw = redis_client.get(key)
    return json.loads(raw) if raw is not None else None

def set_json(key: str, value, ttl: int | None = None) -> None:
    redis_client.set(key, json.dumps(value, ensure_ascii=False),
                     ex=ttl or settings.redis_default_ttl)

def delete(*keys: str) -> int:
    return redis_client.delete(*keys) if keys else 0
```

三个设计点：

| 设计 | 为什么 |
| --- | --- |
| `user_key()` 只在这一处定义 | 防止某处拼成 `users:1`、另一处拼成 `user_1`，导致缓存永远不命中 |
| 统一用 JSON 序列化 | Redis 只能存字符串，Python 对象要先转 |
| `ensure_ascii=False` | 中文原样存，`redis-cli` 里看着舒服 |
| 默认带 TTL | 防止有人忘了传，key 永不过期 |

> **通俗理解**：`cache.py` 是"小本子的统一写法"——怎么起 title、怎么写、怎么撕，全公司一套规矩，谁都不许自己发明。

## 3.5 关键决策：缓存 DTO，不缓存 ORM 对象

### 3.5.1 两种写法

**错误写法**：把 `User` 对象存进去

```python
user = db.get(User, 1)
redis_client.set("user:1", pickle.dumps(user))     # ❌ 不要这样做
```

**正确写法**：转成 Pydantic 模型再存

```python
out = UserOut.model_validate(user)                  # ORM -> DTO
cache.set_json(key, out.model_dump(mode="json"))    # DTO -> 普通字典
```

### 3.5.2 为什么不能用 ORM 对象

| 问题 | 说明 |
| --- | --- |
| `DetachedInstanceError` | ORM 对象和 Session 绑定，Session 关了再访问属性就报错 |
| 不能直接 JSON 序列化 | `User` 对象里是 `Decimal`、`datetime`、还有关系属性 |
| 偷偷触发查询 | 访问 `user.orders` 会去查数据库，缓存反而变慢 |
| 结构耦合 | 表结构一改，缓存里的旧对象就废了 |

而 `UserOut.model_dump(mode="json")` 出来的是**纯字典**：

```json
{"id": 1, "username": "张三", "phone": "13800000001",
 "balance": "888.00", "is_deleted": false, "created_at": "2026-11-03T16:07:59"}
```

可以安全地存、安全地取。

> **通俗理解**：ORM 对象像"还插在数据库上的网线"，拔了就废；DTO 像"打印出来的一张纸"，复印、传阅都没问题。缓存里要存纸，不能存网线。

## 3.6 读路径改造

### 3.6.1 新增 `user_cache.py`

```python
def get_user_out(db: Session, user_id: int) -> UserOut:
    key = cache.user_key(user_id)

    cached = cache.get_json(key)
    if cached is not None:
        return UserOut.model_validate(cached)      # 命中

    user = user_service.get_user(db, user_id)      # 未命中, 查库; 查不到抛 404
    out = UserOut.model_validate(user)

    cache.set_json(key, out.model_dump(mode="json"))
    return out
```

### 3.6.2 路由改一行

```python
# 改前
@router.get("/{user_id}", response_model=UserOut, summary="用户详情")
def get_user(user_id: int, db: Session = Depends(get_db)) -> UserOut:
    return user_service.get_user(db, user_id)

# 改后
@router.get("/{user_id}", response_model=UserOut, summary="用户详情(带缓存)")
def get_user(user_id: int, db: Session = Depends(get_db)) -> UserOut:
    return user_cache.get_user_out(db, user_id)
```

**404 不会被缓存**：因为 `user_service.get_user` 在查不到时直接抛异常，代码走不到 `set_json`。

如果要防"穿透"（第二章 2.5），需要在 `get_user` 里额外处理，本项目暂不做——那是下一层的优化。

## 3.7 写路径：改完库要删缓存

三个写操作都要删：

```python
def update_balance(db, user_id, amount) -> User:
    ...
    db.commit()
    db.refresh(user)
    cache.delete(cache.user_key(user_id))      # 改完库再删, 顺序不能反
    return user

def soft_delete(db, user_id) -> User:
    ...
    db.commit()
    cache.delete(cache.user_key(user_id))

def hard_delete(db, user_id) -> None:
    ...
    db.commit()
    cache.delete(cache.user_key(user_id))
```

转账要删两个：

```python
def transfer(db, from_id, to_id, amount):
    ...
    db.commit()
    db.refresh(src)
    db.refresh(dst)
    cache.delete(cache.user_key(from_id), cache.user_key(to_id))
```

**注意**：`assign_role` 不用删——`UserOut` 里没有 `roles` 字段，角色变更不影响用户详情的缓存内容。

| 操作 | 要不要删缓存 | 原因 |
| --- | --- | --- |
| 新建用户 | 不用 | 新用户还没有缓存 |
| 改余额 | 要 | `balance` 在 `UserOut` 里 |
| 软删 / 硬删 | 要 | `is_deleted` 在 `UserOut` 里 |
| 转账 | 要删两个 | 两边余额都变了 |
| 分配角色 | 不用 | `roles` 不在 `UserOut` 里 |

## 3.8 实测：命中缓存后一条 SQL 都不发

案例文件：`redis_notes/ch03/code/01_cache_in_project.py`

它用 SQLAlchemy 的事件钩子统计每条请求的 SELECT 条数：

```plain
--- ② 连续请求详情接口 3 次, 每次都统计 SQL ---
    第 1 次: 状态码 200, 用户名 张三, 发了 1 条 SELECT
             SQL: SELECT users.id, users.username, users.phone, ...
    第 2 次: 状态码 200, 用户名 张三, 发了 0 条 SELECT
    第 3 次: 状态码 200, 用户名 张三, 发了 0 条 SELECT

--- ③ 缓存的内容与剩余时间 ---
    缓存 key : user:1
    剩余秒数 : 300
    缓存内容 : {"id": 1, "username": "张三", "phone": "13800000001", "balance": "888.00", ...}
```

**从 1 条 SELECT 降到 0 条**——这才是缓存真正省下来的东西。

## 3.9 失效：改完马上就没

案例文件：`redis_notes/ch03/code/02_invalidation.py`

```plain
--- ① 先清缓存 ---
    清理后              缓存存在: False, 剩余 -2 秒

--- ② 查一次详情: 未命中 -> 查库 -> 回写缓存 ---
    余额: 400.00
    查完之后             缓存存在: True, 剩余 300 秒

--- ④ 改余额: 先改库, 再删缓存 ---
    改完余额: 401.00
    改完之后             缓存存在: False, 剩余 -2 秒

--- ⑤ 再查: 缓存被删了, 重新查库并回写 ---
    余额: 401.00 (已经是最新值)
    重建之后             缓存存在: True, 剩余 300 秒
```

`ttl` 返回 `-2` 就是"key 不存在"，正好用来确认删成功了。

## 3.10 测试怎么验证缓存

`project/tests/test_cache.py` 新增 5 个用例：

| 用例 | 验证什么 |
| --- | --- |
| `test_detail_creates_cache` | 第一次查详情会写缓存，且 TTL > 0 |
| `test_detail_hits_cache` | 第二次查命中缓存（篡改缓存值，接口返回也跟着变） |
| `test_update_balance_invalidates` | 改余额后缓存被删 |
| `test_soft_delete_invalidates` | 软删除后缓存被删 |
| `test_404_is_not_cached` | 查不存在的用户返回 404，且不写缓存 |

**"篡改缓存"那个用例最巧妙**：

```python
client.get(f"/users/{uid}")                 # 先让缓存写进去
fake = cache.get_json(key)
fake["username"] = "缓存里的名字"
cache.set_json(key, fake)                   # 改掉缓存

r = client.get(f"/users/{uid}")
assert r.json()["username"] == "缓存里的名字"   # 接口返回的是缓存里的值
```

如果接口返回的还是数据库里的名字，说明**根本没走缓存**——这比"看 Redis 里有没有 key"更能证明命中。

运行：

```plain
13 passed in 1.00s
```

（8 个原有认证用例 + 5 个新增缓存用例）

## 3.11 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `ConnectionRefusedError` | Redis 没启动 | `docker start mysql-learn-redis` |
| 缓存永远是空的 | key 拼错（`users:1` vs `user:1`） | 统一用 `cache.user_key()` |
| `TypeError: Object of type Decimal is not JSON serializable` | 直接 `json.dumps(ORM对象)` | 先 `UserOut.model_validate` 再 `model_dump(mode="json")` |
| 改完数据还是旧值 | 写操作忘了删缓存 | 每个写函数 `commit` 后加 `cache.delete` |
| `DetachedInstanceError` | 把 ORM 对象塞进了缓存 | 缓存 DTO，不缓存 ORM |
| 缓存里全是 bytes | 没开 `decode_responses` | 连接池参数加上 |
| 测试之间互相影响 | 缓存没清 | 每个用例开头 `redis_client.delete(key)` |

## 3.12 本章小结

1. 缓存加在 **service 层**，路由只调一行；key 命名集中在一处，避免拼错导致永不命中。
2. **缓存 DTO，不缓存 ORM 对象**：ORM 对象与 Session 绑定，取出来会 detached。
3. 读路径：查缓存 → 未命中查库 → 回写。写路径：改库 → 删缓存（顺序不能反）。
4. 只有影响 `UserOut` 字段的操作才需要删缓存；分配角色不需要。
5. 实测：命中缓存后详情接口发 **0 条 SELECT**，未命中才 1 条。
6. 测试用"篡改缓存再看接口返回"来证明命中，比检查 key 是否存在更有说服力。
7. 缓存接进项目只改了 5 个文件 + 加 1 个测试文件，业务代码几乎没动。
