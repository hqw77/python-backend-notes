# Redis 第二章 · 缓存设计与三大问题

## 2.1 学习目标

第一章讲了 Redis 的语法，这一章讲**怎么用它做缓存而不出事**。学完应该能做到：

1. 说清缓存到底省掉了什么，什么是命中率
2. 掌握 Cache-Aside 的读写路径，知道为什么写操作是"删缓存"而不是"更新缓存"
3. 分清穿透、击穿、雪崩三者的成因与应对
4. 理解"先改库还是先删缓存"的取舍，知道脏数据窗口在哪
5. 能设计 key 与 TTL

前置知识：第一章（五种类型、TTL、`set nx ex`）。

> **本章的读法**：每个问题都按"现象 → 实测 → 为什么 → 怎么防"讲。
> 三个案例都不依赖 `project/`，用一个 50 毫秒延迟的假数据库模拟慢查询。

## 2.2 缓存到底解决什么问题

### 2.2.1 一个查询的时间花在哪

假设一个"查用户详情"的接口，直接查 MySQL：

```plain
   请求进来
      │
      ├─ 从连接池借一条连接       约 1 ms
      ├─ 发 SQL、网络往返         约 1 ms
      ├─ MySQL 解析 + 执行 + 返回  1~5 ms
      └─ 转成 JSON 返回            约 1 ms
      ─────────────────────────────────────
      合计 4~8 ms

   如果这一秒来了 1000 个请求，数据库就得干 1000 次活
```

加连接池只是让"借连接"更快，**数据库那一趟还是省不掉**。

缓存的做法是把结果放在内存里：

```plain
   第一次请求：查 MySQL → 结果写进 Redis → 返回          8 ms
   之后请求：  直接读 Redis → 返回                       0.3 ms
```

### 2.2.2 命中率

| 概念 | 含义 |
| --- | --- |
| **命中** | 请求的数据在缓存里，直接返回 |
| **未命中** | 缓存里没有，要去查数据库，然后写回缓存 |
| **命中率** | 命中次数 / 总请求数 |

命中率 90% 意味着：1000 个请求里只有 100 个真的打到数据库。

> **通俗理解**：MySQL 是仓库，Redis 是收银台旁边的小货架。顾客要什么先看货架，没有再去仓库，拿回来顺手摆上货架。货架上的东西越多、越常卖，跑仓库的次数就越少。

### 2.2.3 哪些数据适合缓存

| 特征 | 适合吗 | 例子 |
| --- | --- | --- |
| 读多写少 | ✅ | 用户详情、商品信息、配置项 |
| 能容忍短暂旧值 | ✅ | 文章阅读数、推荐列表 |
| 查询很慢 | ✅ | 多表聚合、报表 |
| 要求强一致 | ❌ | 账户余额的实时校验、库存扣减 |
| 数据量极大 | ❌ | 全量日志、历史订单 |

**关键判断**：这份数据"晚 5 分钟更新"能不能接受？能，就可以缓存。

## 2.3 四种缓存模式

### 2.3.1 对比

| 模式 | 读怎么做 | 写怎么做 | 特点 |
| --- | --- | --- | --- |
| **Cache-Aside** | 应用先读缓存，没有就查库并回写 | 应用改库后删缓存 | 最常用，逻辑全在应用里 |
| Read-Through | 缓存层自己去查库 | — | 应用只和缓存打交道 |
| Write-Through | — | 写缓存时同步写库 | 一致性好，但写变慢 |
| Write-Behind | — | 先写缓存，异步批量写库 | 写很快，但可能丢数据 |

### 2.3.2 为什么选 Cache-Aside

三个理由：

1. **简单**：不需要缓存中间件支持特殊功能，任何 Redis 都能用
2. **容错**：Redis 挂了，代码退化成"直接查库"，业务不中断
3. **可控**：缓存什么、缓存多久，都写在业务代码里，看得见

> **通俗理解**：Cache-Aside 就是"自己记账"。读之前先看小本子，没有就去查库记上；改了库就把那页撕掉，下次重新记。撕掉比改写安全——改写容易写错。

## 2.4 Cache-Aside 的读写路径

### 2.4.1 读路径

```python
def get_user_cached(user_id: int):
    key = f"user:{user_id}"

    cached = r.get(key)                      # ① 先查缓存
    if cached is not None:
        return json.loads(cached)            #    命中，直接返回

    user = db.get_user(user_id)              # ② 未命中，查数据库
    if user is None:
        return None

    r.set(key, json.dumps(user), ex=300)     # ③ 写回缓存，5 分钟过期
    return user
```

三步：**查缓存 → 查库 → 回写**。

### 2.4.2 写路径

```python
def update_balance(user_id: int, balance: str):
    db.update_balance(user_id, balance)      # ① 先改数据库
    r.delete(f"user:{user_id}")              # ② 再删缓存
```

两步：**改库 → 删缓存**。

### 2.4.3 为什么是"删"而不是"更新"

假设两个写者同时改同一个对象，都采用"更新缓存"：

```plain
   写者 A：改库为 100 → 更新缓存为 100
   写者 B：改库为 200 → 更新缓存为 200
```

如果 A 改完库、还没更新缓存时，B 抢先更新了缓存，最后可能是：

```plain
   数据库 = 200        缓存 = 100      ← 缓存比数据库旧
```

改成"删缓存"就没这个问题：不管谁先删，下次读都会从数据库重新加载当前值。

| | 更新缓存 | 删除缓存 |
| --- | --- | --- |
| 并发风险 | 可能写进旧值 | 无（下次读重建） |
| 实现复杂度 | 要构造完整对象 | 一行 `delete` |
| 写后第一次读 | 快 | 要查一次库 |

**结论**：删缓存是"让位给下一次读"，简单可靠；更新缓存是"主动出击"，容易出错。

### 2.4.4 本节用到的命令

| 命令 | 中文意思 | 怎么用 | 返回什么 |
| --- | --- | --- | --- |
| `get(key)` | 读一个 key | `get("user:1")` | 值；不存在返回 `None` |
| `set(key, value)` | 写一个 key | `set("user:1", "...")` | `True` |
| `set(key, value, ex=秒)` | 写并设置过期 | `set("user:1", "...", ex=300)` | `True` |
| `delete(key)` | 删一个 key | `delete("user:1")` | 删掉了几个 |
| `exists(key)` | 存在吗 | `exists("user:1")` | `1` 存在 / `0` 不存在 |

### 2.4.5 实测

案例文件：`redis_notes/ch02/code/01_cache_aside.py`

```plain
--- ③ 连续读 100 次: 数据库一次都没被打 ---
    数据库被查       -> 0 次
    100 次总耗时     -> 37.3 ms, 平均 0.37 ms/次

--- ⑥ 对比: 完全不使用缓存 ---
    数据库被查       -> 100 次
    100 次总耗时     -> 5034.2 ms, 平均 50.34 ms/次
```

**0.37 ms vs 50.34 ms，差约 134 倍。**

### 2.4.6 写完之后缓存会怎样

```plain
--- ④ 写操作: 改库 + 删缓存 ---
    改库完成, 已删除缓存 user:1
    缓存还在吗       -> 0 (0 表示已经删掉)

--- ⑤ 写之后再读: 会重新加载最新的值 ---
    结果             -> {'id': 1, 'username': '张三', 'balance': '588.00'}
    数据库被查       -> 1 次 (重建了一次)
```

写完缓存被删，**下一次读才重建**。没人读就不占内存，这叫懒加载。

## 2.5 缓存穿透

### 2.5.1 现象

查询一个**根本不存在**的数据：

```plain
   请求 id=999999
      │
      ├─ 查缓存 → 没有
      ├─ 查数据库 → 没有
      └─ 不写缓存（因为没数据可写）
      ↓
   下一个请求 id=999999 → 又是这个流程
```

每次都会打数据库。如果有人拿大量随机 id 刷，数据库会被打垮。

**和击穿的区别**：穿透是"数据本来就不存在"，击穿是"数据存在但缓存过期了"。

### 2.5.2 实测

```plain
--- ① 穿透: 查一个不存在的 id, 100 次 ---
    数据库被查       -> 100 次  <- 缓存完全没用
```

### 2.5.3 三种应对

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **空值缓存** | 查不到也存一个标记 `"__NULL__"`，TTL 短一点 | 浪费一点内存，但最简单 |
| **布隆过滤器** | 用位数组提前判断"这个 id 一定不存在" | 有误判率，实现复杂 |
| **参数校验** | id 必须是正整数、在合理范围 | 只能挡住一部分 |

### 2.5.4 空值缓存的写法

```python
def read_with_null(user_id: int):
    key = f"null:{user_id}"
    cached = r.get(key)
    if cached is not None:
        return None if cached == "__NULL__" else json.loads(cached)

    user = db.get_user(user_id)
    if user is None:
        r.set(key, "__NULL__", ex=30)        # 关键：把"没有"也缓存起来
        return None

    r.set(key, json.dumps(user), ex=300)
    return user
```

**为什么 TTL 要短（30 秒）**：万一这个 id 是"马上要被创建"的，缓存空值太久会挡住它。

```plain
--- ② 防护后: 把空值也缓存起来 ---
    数据库被查       -> 1 次  <- 只有第一次
```

> **通俗理解**：查不到也记一笔"查过了，没有"。别人再来问，直接告诉他"没有"，不用再跑一趟档案室。

## 2.6 缓存击穿

### 2.6.1 现象

某个**热点 key 刚好过期**，大量并发请求同时到达：

```plain
   T=0      热点 key 过期
   T=0.01   1000 个请求同时发现缓存没了
   T=0.02   1000 个请求同时去查数据库   ← 数据库瞬间被压垮
```

关键区别：击穿是**一个** key，穿透是**一堆不存在的** key。

### 2.6.2 实测

```plain
--- ③ 击穿: 热点 key 不存在, 10 个线程同时来 ---
    数据库被查       -> 10 次  <- 全部穿透
```

### 2.6.3 互斥锁方案

思路：只让一个请求去查库，其余等它把缓存写好。

```python
got = r.set("hot:lock", "1", nx=True, ex=5)     # 抢锁
if got:
    try:
        value = db.get_user(1)                  # 只有抢到锁的去查库
        r.set("hot", value, ex=300)
    finally:
        r.delete("hot:lock")                     # 一定要释放
else:
    time.sleep(0.1)                             # 没抢到就等会儿再读
    return r.get("hot")
```

这里用到的命令：

| 命令 | 中文意思 | 参数说明 |
| --- | --- | --- |
| `set(key, value, nx=True)` | 只有 key **不存在**时才写 | `nx` = Not eXists |
| `set(key, value, ex=5)` | 同时设 5 秒过期 | `ex` = EXpire，单位秒 |
| `delete(key)` | 释放锁 | — |

**为什么必须设 `ex`**：如果抢到锁的进程崩了、没执行到 `delete`，这个锁就永远不会释放，所有请求都会卡住。设了 5 秒过期，最坏情况 5 秒后自动解锁。

```plain
--- ④ 防护后: 加互斥锁, 只放一个线程进去 ---
    数据库被查       -> 1 次  <- 只有拿到锁的那个
```

### 2.6.4 其他方案

| 方案 | 说明 | 适用 |
| --- | --- | --- |
| 逻辑过期 | 缓存不设物理 TTL，值里带一个"逻辑过期时间"，由后台异步刷新 | 要求高可用、不能阻塞 |
| 提前预热 | 启动或定时把热点数据加载进缓存 | 可预测的热点 |
| 永不过期 + 后台更新 | 业务侧永远读缓存，后台定时刷新 | 极热数据 |

> **通俗理解**：击穿就是"网红店开门那一刻，一千人同时冲进去"。互斥锁是"门口排队，一次进一个"；逻辑过期是"店从来没关过，只是后面有人补货"。

## 2.7 缓存雪崩

### 2.7.1 现象

**大批 key 在同一时刻过期**：

```plain
   20:00:00   1000 个 key 一起过期
              （因为它们都在 19:55:00 写入，TTL 都是 300 秒）
   20:00:01   数据库收到 1000 倍流量
```

击穿是一个 key，雪崩是一批 key。**雪崩往往是自己埋的雷**——批量导入缓存时用了统一的 TTL。

### 2.7.2 实测

```plain
--- ⑤ 雪崩: 20 个 key 用同一个 TTL ---
    前 5 个 key 的 ttl -> [60, 60, 60, 60, 60]
    注: 完全一样, 会同一秒集体过期
```

### 2.7.3 TTL 抖动

给 TTL 加随机量，把过期时间打散：

```python
ttl = 60 + random.randint(0, 30)     # 60~90 秒之间随机
r.set(f"jitter:{i}", i, ex=ttl)
```

```plain
--- ⑥ 防护后: TTL 加随机抖动 ---
    前 5 个 key 的 ttl -> [66, 82, 64, 82, 79]
    注: 被打散了
```

### 2.7.4 其他方案

| 方案 | 说明 |
| --- | --- |
| 多级缓存 | 进程内本地缓存 + Redis，Redis 挂了还有本地兜底 |
| 熔断降级 | 数据库压力过大时，直接返回兜底数据 |
| 高可用 | Redis 主从 / 哨兵 / 集群，避免缓存本身成为单点 |

> **通俗理解**：雪崩是"全城超市约好同一分钟补货，结果顾客同时涌进来"。TTL 抖动就是让各家错开补货时间。

## 2.8 缓存与数据库的一致性

### 2.8.1 两种写顺序

| 顺序 | 步骤 | 结果 |
| --- | --- | --- |
| **A（错误）** | 删缓存 → 改库 | 并发下缓存可能长时间是旧值 |
| **B（推荐）** | 改库 → 删缓存 | 最坏只是短暂读到旧值，随后自愈 |

### 2.8.2 路径 A 为什么有问题

案例文件：`redis_notes/ch02/code/03_consistency.py`

```plain
--- ① 路径 A: 先删缓存, 再改数据库(有问题的写法) ---
    初始         数据库=888.00   缓存={"id": 1, "balance": "888.00"}
    写线程: 先删除缓存
    删缓存后       数据库=888.00   缓存=None
    读线程: 缓存没了 -> 查库拿到旧值 888 -> 写回缓存
    读回写后       数据库=888.00   缓存={"id": 1, "balance": "888.00"}
    写线程: 现在才把数据库改成 588
    改库后        数据库=588.00   缓存={"id": 1, "balance": "888.00"}
    !! 缓存还是 888, 数据库是 588, 脏数据会一直留到过期
```

问题出在"删缓存"和"改库"之间的窗口：**读线程在这个窗口里把旧值写回了缓存**。

### 2.8.3 路径 B 为什么更安全

```plain
--- ② 路径 B: 先改数据库, 再删缓存(推荐写法) ---
    初始         数据库=888.00   缓存={"id": 1, "balance": "888.00"}
    写线程: 先把数据库改成 588
    改库后        数据库=588.00   缓存={"id": 1, "balance": "888.00"}
    写线程: 再删除缓存
    删缓存后       数据库=588.00   缓存=None
    读线程: 未命中 -> 查库拿到 588 -> 写回
    读回写后       数据库=588.00   缓存={"id": 1, "balance": "588.00"}
    OK 最坏情况只是有人短暂读到旧值, 之后会自愈
```

因为"改库"在前，读线程即使抢在删缓存之前回写，写的也是**最新值**；删缓存发生在最后，会把可能存在的旧值清掉。

> **通俗理解**：先改账本，再撕小本子。这样无论谁什么时候翻小本子，记的都不会比账本新——最坏是小本子空着，去查账本。

### 2.8.4 删缓存失败了怎么办

| 方案 | 做法 | 说明 |
| --- | --- | --- |
| 延迟双删 | 改库后 `delete`，等 500ms 再 `delete` 一次 | 覆盖那个窗口里被回写的旧值 |
| 队列重试 | 删除失败的丢进消息队列，后台重试 | 保证最终删掉 |
| 短 TTL 兜底 | 缓存设 1~5 分钟过期 | 最多脏几分钟 |

**注意**：这三种都是"降低概率"，不是"绝对一致"。要强一致，只能不缓存，或用 binlog 订阅（如 Canal）异步刷新。

## 2.9 key 与 TTL 的设计

### 2.9.1 key 怎么起名

```plain
业务:对象:标识         user:42     order:2024:88
带环境前缀             prod:user:42     dev:user:42
带版本（结构变更后）    user:v2:42
```

三个要求：**可读、可按前缀批量匹配、不与别的业务冲突**。

### 2.9.2 TTL 怎么定

| 数据 | 建议 TTL | 理由 |
| --- | --- | --- |
| 用户详情 | 5~10 分钟 | 变更不频繁，短暂旧值可接受 |
| 商品库存 | 10~30 秒 | 要求较新 |
| 配置项 | 1 小时 | 极少变 |
| 验证码 | 60~300 秒 | 本身就是临时的 |
| **空值缓存** | 30 秒 | 太长会挡住"后来才创建"的数据 |

### 2.9.3 两条硬规定

1. **所有缓存 key 必须有 TTL**——没有 TTL 的 key 会一直占内存
2. **TTL 要加随机抖动**——批量写入时尤其重要

## 2.10 本章用到的 Redis 命令汇总

| 命令 | 中文意思 | 用在哪 |
| --- | --- | --- |
| `get(k)` | 读缓存 | 读路径第 ① 步 |
| `set(k, v, ex=n)` | 写缓存并设过期 | 读路径第 ③ 步 |
| `set(k, v, nx=True, ex=n)` | 抢锁（不存在才写） | 击穿的互斥锁 |
| `delete(k)` | 删缓存 / 释放锁 | 写路径、finally |
| `exists(k)` | 判断缓存还在不在 | 调试、验证 |
| `ttl(k)` | 还剩多少秒 | 检查是否忘了设过期 |
| `scan_iter("前缀:*")` | 按前缀遍历 key | 批量清理 |

## 2.11 常见错误

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 数据库 QPS 突然飙高 | 热点 key 过期引发击穿 | 互斥锁 / 逻辑过期 / 预热 |
| 缓存和数据库长期不一致 | 用了"先删缓存再改库" | 改成"先改库再删缓存" |
| 大量 key 同时失效 | TTL 统一 | 加随机抖动 |
| 查不存在的数据也压库 | 没做空值缓存 | 存 `"__NULL__"`，TTL 30 秒 |
| 内存一路上涨 | 有 key 没设 TTL | 检查所有 `set` 是否带 `ex` |
| 锁不释放导致全卡住 | 抢锁后没 `delete`，或没设 `ex` | `finally` 里释放 + `ex` 兜底 |
| 缓存里全是 bytes | 没开 `decode_responses` | 连接时加上 |

## 2.12 本章小结

1. 缓存省掉的是"查数据库"这一整段，实测 0.37 ms vs 50.34 ms，差约 134 倍。
2. Cache-Aside：读时"查缓存 → 查库 → 回写"，写时"改库 → 删缓存"。
3. 写操作是**删缓存**不是更新缓存，因为更新容易在并发下写进旧值。
4. 穿透是查不存在的数据，用空值缓存（实测 100 → 1 次）。
5. 击穿是热点 key 过期，用 `set nx ex` 做互斥锁（实测 10 → 1 次）。
6. 雪崩是批量 key 同时过期，用 TTL 随机抖动打散。
7. 写路径必须"先改库、后删缓存"；删失败可用延迟双删或短 TTL 兜底。
8. 所有缓存 key 必须有 TTL，且尽量加抖动。

---

## 2.13 练习

1. 把案例 1 的 TTL 改成 5 秒，连续读 6 秒后再读，观察数据库查询次数的变化。
2. 给案例 2 的互斥锁加一个"等待超时"：抢不到锁最多等 1 秒，超时就返回旧值。
3. 实现延迟双删：改库 → 删缓存 → `sleep(0.5)` → 再删一次，并解释为什么是 0.5 秒。
4. 思考：如果业务要求"用户改了昵称必须立刻看到新名字"，缓存策略要怎么调整？
