## 2.2 缓存的基本模式

### 2.2.1 四种模式

| 模式 | 读 | 写 | 特点 |
| --- | --- | --- | --- |
| **Cache-Aside** | 应用先读缓存,未命中查库并回写 | 应用改库后删缓存 | 最常用,应用自己管缓存 |
| Read-Through | 缓存层负责查库 | — | 应用只和缓存打交道 |
| Write-Through | — | 写缓存时同步写库 | 一致性好,写慢 |
| Write-Behind | — | 先写缓存,异步批量写库 | 写快,可能丢数据 |

### 2.2.2 为什么选 Cache-Aside

三条理由：

1. **实现简单**：不依赖特定缓存中间件的特性,任何缓存都能用；
2. **容错好**：Redis 挂了,代码退化成"直接查库",业务不中断；
3. **可控**：什么时候缓存、缓存多久,全在业务代码里写明。

> **通俗理解**：Cache-Aside 就是"自己记账"。读之前先看小本子,没有就去查库记上；改了库就把那页撕掉,下次重新记。撕掉比改写安全——改写容易写错。

## 2.3 Cache-Aside 的完整路径

### 2.3.1 读路径

```python
def get_user_cached(user_id: int):
    key = f"user:{user_id}"

    cached = r.get(key)                 # ① 先查缓存
    if cached is not None:
        return json.loads(cached)       #    命中,直接返回

    user = db.get_user(user_id)         # ② 未命中,查数据库
    if user is None:
        return None

    r.set(key, json.dumps(user, ensure_ascii=False), ex=300)   # ③ 回写
    return user
```

三步：**查缓存 → 查库 → 回写**。

### 2.3.2 写路径

```python
def update_balance(user_id: int, balance: str):
    db.update_balance(user_id, balance)     # ① 先改数据库
    r.delete(f"user:{user_id}")             # ② 再删缓存
```

两步：**改库 → 删缓存**。

### 2.3.3 为什么是"删"而不是"更新"

假设有两个写者同时改同一个对象：

```plain
   写者 A：改库为 100 → 更新缓存为 100
   写者 B：改库为 200 → 更新缓存为 200
```

如果 A 更新完数据库、还没更新缓存时,B 抢先更新了缓存,那么最后缓存里可能是 100、数据库里是 200——**缓存比数据库旧**。

改成"删缓存"就没这个问题：无论谁先删,下次读都会从数据库重新加载当前值。

| | 更新缓存 | 删除缓存 |
| --- | --- | --- |
| 并发风险 | 可能写进旧值 | 无（下次读重建） |
| 实现复杂度 | 需要构造完整对象 | 一行 `delete` |
| 一次写后多次读 | 读得更快 | 第一次读要查库 |

结论：**更新缓存是"主动出击",容易出错；删缓存是"让位给下一次读",简单可靠。**

### 2.3.4 实测数据

案例文件：`redis_notes/ch02/code/01_cache_aside.py`

用 50ms 延迟的假数据库模拟慢查询：

```plain
--- ③ 连续读 100 次：只有第一次查库 ---
    数据库查询次数: 0
    100 次总耗时: 33.5 ms  平均 0.34 ms/次

--- ⑥ 对比：不走缓存要多久 ---
    100 次总耗时: 5039.6 ms  平均 50.40 ms/次
```

**0.34 ms vs 50.40 ms,差约 150 倍。**

> **通俗理解**：缓存省掉的不是"算得快一点",而是"根本不用去查"。就像问同事一个数字,他记得（缓存）和让他去档案室翻（数据库）,差别是量级的。

### 2.3.5 写之后缓存会怎样

```plain
--- ④ 写操作：改库 + 删缓存 ---
    [写] 改库完成,已删除缓存 demo:aside:user:1
    缓存还在吗: 0

--- ⑤ 写后再读：会重新加载到最新值 ---
    结果: {'id': 1, 'username': '张三', 'balance': '588.00'}
    数据库查询次数: 1  ← 重建了一次
```

写完之后缓存被删,下一次读会重新加载。这就是"懒加载"的好处：**没人读就不浪费内存**。

## 2.4 缓存穿透

### 2.4.1 现象

查询一个**根本不存在**的 key：

```plain
   请求 id=999999
      │
      ├─ 查缓存 → 没有
      ├─ 查数据库 → 没有
      └─ 不写缓存（因为没数据）
      ↓
   下一个请求 id=999999 → 还是这个流程
```

每次都会打数据库,缓存完全没起作用。

恶意攻击者可以用大量随机 id 把数据库打垮。

### 2.4.2 实测

```plain
--- ① 穿透：查询一个不存在的 id,100 次 ---
    数据库被查了 100 次  ← 缓存毫无作用
```

### 2.4.3 三种应对

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **空值缓存** | 查不到也存一个 `"__NULL__"`,TTL 短一些 | 内存浪费一点,但简单有效 |
| **布隆过滤器** | 用位数组提前判断"这个 id 一定不存在" | 有误判率,实现复杂 |
| **参数校验** | id 必须为正整数、且在合理范围 | 只能挡住一部分 |

空值缓存的实现：

```python
if user is None:
    r.set(key, "__NULL__", ex=30)     # 短 TTL,避免长期占用内存
    return None
```

实测：

```plain
--- ② 防护后：把空值也缓存 ---
    数据库被查了 1 次  ← 只有第一次
```

> **通俗理解**：查不到的东西也记一笔"查过了,没有"。这样别人再问,直接告诉他"没有",不用再跑一趟档案室。

## 2.5 缓存击穿

### 2.5.1 现象

某个**热点 key 刚好过期**,此时大量并发请求同时到达：

```plain
   T=0     热点 key 过期
   T=0.01  1000 个请求同时发现缓存没了
   T=0.02  1000 个请求同时去查数据库  ← 数据库瞬间被压垮
```

注意区别：击穿是**一个** key,穿透是**一堆不存在的** key。

### 2.5.2 实测

```plain
--- ③ 击穿：热点 key 不存在,10 个线程同时来 ---
    数据库被查了 10 次  ← 全部穿透
```

### 2.5.3 互斥锁方案

只让一个请求去查库,其余的等它写完缓存再读：

```python
lock_key = f"{key}:lock"
if r.set(lock_key, "1", nx=True, ex=5):      # 抢到锁
    try:
        user = db.get_user(user_id)
        r.set(key, json.dumps(user), ex=300)
    finally:
        r.delete(lock_key)
else:                                         # 没抢到,等一会儿直接读缓存
    time.sleep(0.1)
    return r.get(key)
```

实测：

```plain
--- ④ 防护后：加互斥锁,只放一个进去 ---
    数据库被查了 1 次  ← 只有拿到锁的那个
```

**其他方案**：

- **逻辑过期**：缓存不设物理 TTL,在 value 里存一个"逻辑过期时间",由后台线程异步刷新；
- **缓存预热**：启动或定时把热点数据提前加载进缓存,避免过期瞬间的真空。

> **通俗理解**：击穿就是"网红店开门那一刻,一千人同时冲进去"。互斥锁是"门口排队,一次进一个"；逻辑过期是"店从来没关过,只是换货时有人在后面补"。

## 2.6 缓存雪崩

### 2.6.1 现象

**大批 key 在同一时刻过期**,请求全部落到数据库：

```plain
   20:00:00  1000 个 key 一起过期（因为它们都在 19:55:00 写入,TTL 都是 300 秒）
   20:00:01  数据库收到 1000 倍流量
```

击穿是一个 key,雪崩是一批 key。**雪崩往往是自己埋的雷**——批量导入缓存时用了统一的 TTL。

### 2.6.2 实测

```plain
--- ⑤ 雪崩：20 个 key 用同一个 TTL ---
    前 5 个 key 的 TTL: [60, 60, 60, 60, 60]  ← 完全一样,会同一秒集体过期
```

### 2.6.3 TTL 抖动

给 TTL 加一个随机量,把过期时间打散：

```python
ttl = 60 + random.randint(0, 30)      # 60~90 秒之间随机
r.set(key, value, ex=ttl)
```

实测：

```plain
--- ⑥ 防护后：TTL 加随机抖动 ---
    前 5 个 key 的 TTL: [81, 86, 63, 66, 66]  ← 被打散了
```

**其他方案**：

| 方案 | 说明 |
| --- | --- |
| 多级缓存 | 本地缓存（进程内）+ Redis,Redis 挂了还有本地兜底 |
| 熔断降级 | 数据库压力过大时,直接返回兜底数据或稍后重试 |
| 预热 + 永不过期 | 后台定时刷新,业务侧不依赖 TTL |
| 高可用 | Redis 主从 / 哨兵 / 集群,避免单点故障本身引发雪崩 |

> **通俗理解**：雪崩就是"全城的超市约好同一分钟补货,结果所有顾客同时涌进来"。TTL 抖动就是让各家错开补货时间。

## 2.7 缓存与数据库的一致性

### 2.7.1 两种顺序

| 顺序 | 步骤 | 结果 |
| --- | --- | --- |
| **A（错误）** | 删缓存 → 改库 | 并发下缓存可能永久是旧值 |
| **B（推荐）** | 改库 → 删缓存 | 最坏只是短暂读到旧值,随后自愈 |

### 2.7.2 路径 A 的问题

案例文件：`redis_notes/ch02/code/03_consistency.py`

```plain
    初始           数据库=888.00 缓存={"id": 1, "balance": "888.00"}
    写线程：删除缓存
    删缓存后         数据库=888.00 缓存=None
    读线程：缓存没了 → 查库拿到旧值 888 → 回写缓存
    读回写后         数据库=888.00 缓存={"id": 1, "balance": "888.00"}
    写线程：现在才更新数据库为 588
    改库后          数据库=588.00 缓存={"id": 1, "balance": "888.00"}
    ⚠️ 缓存里是 888,数据库是 588,而且这个脏值会一直留到 TTL 过期
```

问题出在"删缓存"和"改库"之间的窗口：**读线程在这个窗口里把旧值写回了缓存**。

### 2.7.3 路径 B 为什么更安全

```plain
    写线程：先更新数据库为 588
    写线程：再删除缓存
    读线程：未命中 → 查库拿到 588 → 回写
    ✅ 最坏情况只是有一个读者短暂读到旧值,之后自愈
```

因为"改库"在前,读线程即使抢在删缓存之前回写,写的是**最新值**；而删缓存发生在最后,会把可能存在的旧值清掉。

> **通俗理解**：先改账本,再撕小本子。这样无论谁什么时候翻小本子,记的都不会比账本新——最坏是小本子空着,去查账本。

### 2.7.4 删缓存失败了怎么办

三种补充方案：

1. **延迟双删**：改库后 `delete`,等 500ms 再 `delete` 一次,覆盖那个窗口里被回写的旧值；
2. **消息队列重试**：删除失败的操作入队,后台重试直到成功；
3. **短 TTL 兜底**：即使删失败,几分钟后缓存自己过期。

**注意**：这三种都是"降低概率",不是"绝对一致"。要强一致,只能不缓存,或者用 binlog 订阅（如 Canal）异步刷新。

## 2.8 key 设计与 TTL 策略

### 2.8.1 key 的命名

```plain
业务:对象:标识         user:42    order:2024:88
带环境                prod:user:42    dev:user:42
带版本（结构变更时）   user:v2:42
```

三个要求：**可读、可批量匹配、不与别的业务冲突**。

### 2.8.2 TTL 怎么定

| 数据 | 建议 TTL | 理由 |
| --- | --- | --- |
| 用户详情 | 5~10 分钟 | 变更不频繁,短暂旧值可接受 |
| 商品库存 | 10~30 秒 | 要求较新,且用锁保证扣减正确 |
| 配置项 | 1 小时 | 极少变 |
| 验证码 | 60~300 秒 | 本身就是临时的 |
| 空值缓存 | 30 秒 | 太长会挡住"后来才创建"的数据 |

**原则**：TTL 不是"越长越好"。缓存只是加速层,真正的数据在 MySQL。

### 2.8.3 必须遵守的两条

1. **所有缓存 key 必须有 TTL**——没有 TTL 的 key 会一直占内存；
2. **TTL 要加抖动**——批量写入时尤其重要。

## 2.9 常见错误

| 现象 | 原因 | 解决方法 |
| --- | --- | --- |
| 数据库 QPS 突然飙高 | 热点 key 过期引发击穿 | 互斥锁 / 逻辑过期 / 预热 |
| 缓存和数据库长期不一致 | 用了"先删缓存再改库" | 改为"先改库再删缓存" |
| 缓存大量 key 同时失效 | TTL 统一 | 加随机抖动 |
| 查到不存在的数据也压库 | 没做空值缓存 | 存 `"__NULL__"`,TTL 30 秒 |
| 内存一路上涨 | key 没设 TTL | 检查所有 `set` 是否带 `ex` |
| `WRONGTYPE` 报错 | 同一个 key 类型混用 | key 命名里区分类型 |
| 缓存里是 bytes 用不了 | 忘了 `decode_responses=True` | 连接时加上 |

## 2.10 本章小结

1. 缓存首选 Cache-Aside：读时"查缓存 → 查库 → 回写",写时"改库 → 删缓存"。
2. 读 100 次实测：有缓存 0.34 ms/次,无缓存 50.4 ms/次,差约 150 倍。
3. 穿透是查不存在的数据,用空值缓存或布隆过滤器；实测 100 次压库降到 1 次。
4. 击穿是单个热点 key 过期,用互斥锁让一个请求去查库；实测 10 次降到 1 次。
5. 雪崩是批量 key 同时过期,用 TTL 抖动打散过期时间。
6. 写路径必须"先改库、后删缓存"；删缓存失败可用延迟双删、队列重试、短 TTL 兜底。
7. 所有缓存 key 必须有 TTL,且尽量加随机抖动。
